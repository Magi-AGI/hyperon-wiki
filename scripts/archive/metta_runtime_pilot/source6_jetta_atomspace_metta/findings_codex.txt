S6.A.Q1 - jetta frontend / parser
=================================

Verdict: [JETTA-ANTLR-GENERATED-PARSER]

jetta has a hand-written ANTLR grammar, but the parser used by the compiler is generated through the ANTLR Kotlin toolchain, so the best single label is generated-parser rather than custom-parser.

Evidence:

- `frontend/build.gradle.kts:6` applies `id("com.strumenta.antlr-kotlin") version "1.0.0-RC2"`.
- `frontend/build.gradle.kts:22` depends on `com.strumenta:antlr-kotlin-runtime`.
- `frontend/build.gradle.kts:44-49` configures the grammar source directory and generated package.
- `frontend/antlr/Jetta.g4:1` declares `grammar Jetta`.
- `frontend/antlr/Jetta.g4:3-14` defines the program/statement/run grammar, including `!` evaluation syntax.
- `frontend/antlr/Jetta.g4:154-156` parses MeTTa-style variables as `DOLLAR identifier`.
- `frontend/antlr/Jetta.g4:262-267` has `if` and `import` tokens; there is no grammar token for `cond`, `bind!`, or `new-space` at main HEAD.
- `frontend/src/main/kotlin/net/singularity/jetta/compiler/parser/antlr/AntlrParserFacadeImpl.kt:3-4` imports generated `JettaLexer` and `JettaParser`.
- `AntlrParserFacadeImpl.kt:15-24` builds `CharStreams`, `CommonTokenStream`, calls `parser.program()`, and visits the generated parse tree.
- `compiler/src/main/kotlin/net/singularity/jetta/compiler/Compiler.kt:18` imports `AntlrParserFacadeImpl`.
- `Compiler.kt:63-70` constructs the parser facade and parses each source.
- `Compiler.kt:99` returns `AntlrParserFacadeImpl()` as the compiler parser facade.

Variable-prefix nuance:

The grammar accepts `$identifier` directly (`Jetta.g4:154-156`). Many Kotlin tests write `_x` and then call `.replace('_', '$')`, so test sources use `_` as a string-literal convenience, not as the source grammar.

S6.A.Q4 - jetta space / matcher / bindings
===========================================

Verdict: [JETTA-SPACE-PERCALL-BINDINGS-EXTENDED]

jetta has a real space/matcher implementation with multivalued matching, persistent-ish serialized spaces, and per-call binding propagation. It is closer to a real runtime than a compiler-only project, but the binding model is an extension, not straightforward Hyperon Space parity.

Evidence:

- `runtime/src/main/kotlin/net/singularity/jetta/runtime/space/SpaceImpl.kt:13-16` defines an in-memory store and pattern indexer map.
- `SpaceImpl.kt:18-23` documents `enablePerCallBindings`, which wraps match results in `BoundAtom` snapshots for "stack foliation".
- `SpaceImpl.kt:25-27` adds expressions to space.
- `SpaceImpl.kt:41-74` implements `match`: creates/uses an `IndexerImpl`, resolves every packed match, substitutes variables into the template, optionally wraps results in `BoundAtom`, and returns a `List<Atom>`.
- `SpaceImpl.kt:85-99` writes resolved bindings into the global `Matcher` binding stack.
- `runtime/src/main/kotlin/net/singularity/jetta/runtime/Matcher.kt:12-16` uses `ThreadLocal` binding stack and depth.
- `Matcher.kt:20-33` pushes a binding frame; `Matcher.kt:36-57` pops and propagates child-frame bindings to the parent.
- `Matcher.kt:63-66` sets a binding; `Matcher.kt:71-85` resolves `BoundAtom` and variables by searching the stack.
- `Matcher.kt:88-89` delegates `Matcher.match` to `Space.match`.
- `backend/src/main/kotlin/net/singularity/jetta/compiler/backend/Externals.kt:70-90` registers `match` and `matchEval` as multivalued system functions returning list/sequence types.
- `backend/src/test/kotlin/net/singularity/jetta/compiler/backend/PerCallBindingTest.kt:15-26` documents the core per-call binding expectation.
- `PerCallBindingTest.kt:28-57` tests `(lookup $x) (match &self (Color $x) $x)` returning both `red` and `blue` when invoked with a variable.
- `PerCallBindingTest.kt:405-443` tests propagated bindings through `(findAll) (ift (check $x) $x)`.

Faithfulness caveat:

The result shape and binding propagation are deliberately "stack foliation" / per-call binding semantics, not a direct claim of Hyperon Space API compatibility. The `SpaceImpl.kt:45` comment says there is no save/restore because bindings must remain visible after `match` returns; that is an implementation choice that should be recorded as extended semantics.

Q-3 catchall multi-reduction
----------------------------

Verdict: [QUIRK-REPRODUCED]

jetta is on the Hyperon/MeTTaLog side of the S3 divergence, not the MeTTaTron most-specific-rule side. Multiple definitions of the same function are rewritten into `Match` branches, marked multivalued, and all matching branches contribute results. Specific + fallback patterns can both fire.

Evidence:

- `frontend/src/main/kotlin/net/singularity/jetta/compiler/frontend/rewrite/FunctionRewriter.kt:181-213` groups multiple patterns for one function into a single `FunctionDefinition` with a `Match` body.
- `FunctionRewriter.kt:196-218` enforces a `multivalued` annotation for multi-pattern functions.
- `FunctionRewriter.kt:159-178` builds branch conditions only for constants/expressions; fallback variable-only patterns have no condition.
- `backend/src/main/kotlin/net/singularity/jetta/compiler/backend/FunctionGenerator.kt:398-413` generates a `List` result for a `Match`, iterates all branches, and returns the accumulated list.
- `FunctionGenerator.kt:466-477` adds branch results to the result list, using `addAll` for `SeqType` and `add` otherwise.
- `backend/src/test/kotlin/net/singularity/jetta/compiler/backend/MatchGeneratorTest.kt:15-31` tests two zero-arg definitions returning `listOf(0, 1)`.
- `MatchGeneratorTest.kt:34-50` tests a specific pattern plus fallback: `(foo 10)` returns `listOf(0, 11)`.
- `MatchGeneratorTest.kt:141-148` documents that both destructured and fallback branches match `(And X Y)`.
- `MatchGeneratorTest.kt:315-322` documents branch 1 plus fallback behavior in a nested example.

This is the important final-source quirk finding: MeTTaTron remains the lone closed-cluster source with a most-specific filter; jetta reproduces the multi-branch/catchall behavior.
